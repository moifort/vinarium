# Continuous integration

One workflow per concern, so a red run names its cause and a change touches one file. Templates
in `templates/.github/workflows/`.

| Workflow | Trigger | What it does |
|---|---|---|
| `test-unit`, `test-int`, `test-feat` | called by `deploy`; pull request | One test family each, run separately on purpose |
| `schema` | push, pull request | Schema compatibility against `main`: a removal without a prior deprecation fails |
| `build-ios` | called by `release-ios`; manual | Builds the app for the simulator, runs the unit test target, the strings catalogue check and the pure-components check. A push to `main` builds no app |
| `deploy` | push to `main`; pull request labelled `staging` | Calls the three test workflows and waits for them, then build, `terraform apply`, migrations; to production from the branch, to staging from a labelled pull request; `paths-ignore` for prose |
| `testflight-ios` | nightly, manual | The nightly: archives and uploads once a night when `main` moved since the last upload, to the internal group, then to the external group through Beta App Review, under the version under development read from the changelog |
| `release-ios` | tag `ios-v<version>` | Version guard against the changelog, `build-ios` first (a failure stops the release), panels upload, submission, source maps |
| `pages` | push touching `site/` | Publishes the site |
| `renovate` | nightly, manual | Self-hosted Renovate with its own token |

## Rules

- The build number is the run number. The marketing version is read from the project.
- `paths-ignore` on deploy, schema and the tests for `site/**`, `docs/**`, `screenshots/**`,
  `README.md`, `CLAUDE.md`; never for the served changelogs.
- A workflow authenticates to Google Cloud through Workload Identity Federation, never a key file.
- Secrets are repository secrets; configuration that is not secret (a billing table, an analytics
  property) is a repository variable.
- The iOS archive signs manually with the certificate and profile stored as secrets; the store API
  key uploads and submits.
- **Nothing reaches production on red tests.** Deploy calls the test workflows (`workflow_call`)
  and its job `needs` them; on `main` they do not run on their own. Each test workflow names its
  `concurrency` group by hand (`tests-unit-${{ github.ref }}`): called from Deploy,
  `github.workflow_ref` is Deploy's, and the three would cancel one another. The Terraform queue
  (`concurrency`, never cancelled) sits on the deploy job, not the workflow, so tests start at once.
- **The app builds at release, not on every push.** A push to `main` does not wait on a macOS
  runner; `release-ios` calls `build-ios` before archiving, and the submission requires it green.
  `build-ios` can be run by hand at any time.
- **A warm iOS build on a fresh runner**: one simulator only (the newest iPhone runtime of the
  image, booted first, while the packages resolve); the Swift packages cached with only the
  simulator slice of each binary framework; the derived data cached per Xcode and package
  versions, with `scripts/stable-mtimes.py` stamping every source with the time of its last
  commit so the restored build is not thrown away. Compare runs by Xcode's timing summary, not
  totals: runners vary twice in speed.
- A failing lint or test in CI is a process failure: it should have been caught before the push
  ([04-push.md](04-push.md)).
